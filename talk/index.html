WebGPU

Running code on the graphics card, from a browser tab, in TypeScript.

There are diagrams throughout and two live demos running alongside: a page of spinning cubes for the drawing half, and a compute page that races the same maths on the GPU and the CPU. Both are linked in the footer and open in another tab, so nothing here is a surprise. Go and break them whenever you like.

The words, up front

Every term on the next 18 slides, in one place. Come back here whenever one stops making sense.

Word What it means
GPU A chip that runs thousands of tiny programs at once, instead of a few fast ones.
WebGPU The browser's API for talking to that chip. A standard, not a library.
WGSL The separate language GPU programs are written in. Reads a lot like Rust.
Shader One of those programs. The name comes from the one that picks colours.
Vertex One corner of a triangle. Every 3D model is a pile of these.
Vertex shader Runs once per corner. Works out where that corner lands on screen.
Rasterizer Fixed hardware between the two shaders. Works out which pixels a triangle covers.
Fragment A pixel a triangle might colour. Might, because something could be in front of it.
Fragment shader Runs once per fragment. Works out what colour it is.
Texture An image sitting in GPU memory that a shader reads from.
Compute shader Same idea, no triangles and no screen. A grid of threads over data you choose.
Thread One run of a shader. It asks for its own id and handles that one element.
Workgroup A block of threads that run together and share a small block of very fast memory.
Dispatch The call that launches a number of workgroups. Where compute work starts.
Buffer A slab of GPU memory. Your data crosses into one of these as raw bytes.
Bind group The wiring that connects your buffers to the slots a shader declares.
Pipeline A shader plus its inputs and output format, built and checked once up front.
Encoder Where commands are recorded, so they can be submitted in one go.

What is WebGPU

A browser API for talking to the GPU directly.

  • It is a standard. A W3C spec, not a library. Shipping in Chrome and Edge 113+, Firefox 141+ and Safari 26+.
  • It is a thin layer. Your calls map onto Vulkan on Linux and Android, Metal on Apple, D3D12 on Windows. The browser translates, it does not emulate.
  • It does two jobs. Draw pictures, and run arbitrary maths. The second one is the new part.
  • Shaders are a separate language. WGSL, a small typed language that compiles to whatever the driver wants.
  • WGSL reads like Rust. The syntax is openly borrowed from it: fn, let and var, the type after the name, -> for the return type, sized primitives like f32 and u32, and @vertex attributes in the place Rust puts #[derive]. That is not a coincidence, and it comes up again at the end.

TDLR:

You upload data into GPU memory, you write a small program that runs on thousands of threads at once, and you hand the GPU a list of commands. Everything else is detail.

Why not just WebGL

WebGL is OpenGL ES from 2007 wearing a browser hat.

WebGL WebGPU
Compute None. Fake it by drawing to a texture and reading pixels back. First class. Compute shaders with no rendering involved.
State One giant global state machine. Bind, set, hope. Explicit objects. A pipeline is built once and validated once.
Checking Every draw call, while the frame is running. Once, when you build the pipeline.
Submission Immediate, one call at a time. Record a command buffer, submit it in one go.
Errors Numeric codes you poll for. Promises, labels and readable messages.

The practical difference: WebGPU is faster to feed, and it lets you use the GPU for work that has nothing to do with pixels.

What a GPU actually is

Not a faster CPU. A differently shaped one.

CPU

  • 8 to 32 cores, each very fast
  • Huge caches, deep branch prediction
  • Optimised for latency: finish one thing quickly
  • Happy with branches, pointers, irregular work

GPU

  • Thousands of narrow lanes, each fairly slow
  • Tiny caches, no branch prediction worth the name
  • Optimised for throughput: finish a million things eventually
  • Lanes move in step with each other, so an if that sends some lanes one way and some the other makes the whole group run both sides

The test for whether the GPU will help

Same instructions, different data, and no element needs to know what any other element is doing. Shading a pixel passes. Walking a linked list fails. If the work does not have that shape, the GPU will lose, and the cost of moving the data across will make it lose badly.

See it: the compute page runs the same Mandelbrot maths on the GPU and the CPU so you can time both.

The mental model

You do not call the GPU. You post it a job and walk away.

  • Separate memory. The GPU cannot see your JavaScript objects. Everything crosses as raw bytes in a buffer you allocate.
  • Separate program. Your shader is compiled source text in another language. It cannot call your functions, print, or allocate.
  • Asynchronous. You record commands into an encoder and submit them. Nothing has happened yet when submit returns.
  • Reading back is expensive. Getting results into JavaScript means a copy plus an await. Push work to the GPU, keep it there, only pull back what you must.

Every GPU program, in six steps

  • Get a device
  • Create buffers and write your data in
  • Compile a shader module
  • Build a pipeline: this shader, these inputs, this output format
  • Record commands into an encoder and submit them
  • Draw to the canvas, or copy results back

The render pipeline

Two stages are yours to write. The rest is fixed hardware.

One drawIndexed call runs this whole chain. For the cubes demo that is 24 vertices of geometry, replayed once per instance, turned into up to about 2 million fragment invocations on a 1080p screen.

See it: the cubes are this whole chain, once per frame.

Vertex shader

Runs once per vertex. Answers one question: where is this point on screen.

  • A vertex is one corner of a triangle. Usually a position in 3D space with some extra data attached, such as which way the surface faces.
  • In: one vertex out of your buffers, plus any values that are the same for the whole draw, like where the camera is.
  • Out: where that corner lands on the screen, which is required, plus anything you want the fragment shader to have later.
  • Cheap, because there are not many corners. A cube has 24. A detailed character has tens of thousands.
  • One shape, drawn many times. The cubes demo stores a single cube and replays those same 24 corners once per cube, each replay carrying its own position, size and colour. That is how one draw call puts every cube on screen.

The rasterizer, in between

      
The step between the two shaders. You cannot change it, but the fragment shader makes no sense
        until you know what it does.

      
    
        
  • Everything you draw is triangles. A cube is 12 of them. A character is thousands. The vertex shader
          has just told the GPU where each of a triangle's three corners landed on the screen.
    • 
        
  • It fills in the middle. Given those three corners, it works out which screen pixels the triangle
          actually covers, and hands each one to the fragment shader.
    • 
        
  • Those pixels are called fragments. A fragment is a pixel the triangle might colour. Might,
          because another triangle could turn out to be in front of it.
    • 
        
  • It blends corner values across the middle, free. Colour the three corners red, green and blue, and a
          point a third of the way in gets a third of each. The same happens to every other value the vertex shader
          attached, and it costs nothing because the hardware does it.
    • 
        
  • It can drop triangles facing away from you. On a solid object, half the triangles are round the back
          where you will never see them. Throwing those out is half the work gone.
    • 
      

      

        This is where the numbers explode. You feed in thousands of corners and get back millions of
        pixels to colour. Anything expensive is far cheaper in the vertex shader, where it runs
        thousands of times instead of millions.
      

    


    

      
Fragment shader

      
Runs once per covered pixel. Answers one question: what colour.

      
    
        
  • In: the blended values the rasterizer handed over, plus shared values and any textures.
    • 
        
  • Out: a colour. That is usually the whole job.
    • 
        
  • Expensive, because this is where your frame time goes. Millions of runs, every frame, 60 times a
          second.
    • 
        
  • Blind. It cannot see the pixel next to it, or what was already on screen there. It gets its own
          inputs and nothing else.
    • 
      

      

        Per pixel, the cube demo works out light coming from the sky and bouncing off the ground,
        direct light from the sun, a highlight where the sun reflects towards the camera, and a
        brightness correction at the end so the mid-tones do not look muddy.
      

      

      

        See it: the MSAA toggle on the cubes page changes how many times this runs
        per pixel.
      

    


    

      
Compute shader

      
No triangles, no pixels, no canvas. A grid of threads over data you choose.

      
    
        
  • You declare a workgroup size in the shader, and dispatch a number of workgroups from
          TypeScript.
    • 
        
  • Each thread asks for its own id and uses it to index the data. Thread 7 handles element 7.
    • 
        
  • You can only dispatch whole workgroups, so if 20 items need 8 threads each you get 24 threads and 4 spare.
          Every compute shader starts by checking whether it ran off the end of the data, and exiting if it did.
    • 
        
  • Every thread in a workgroup can talk to every other one in that workgroup. They share a small block
          of very fast memory that only they can see, so any thread can write a value and any other thread in the group
          can read it. They can also wait for each other: hit a barrier and nobody moves on until all of them have
          arrived. That is the whole point of grouping threads at all.
    • 
        
  • Across workgroups there is nothing. No shared memory, no waiting, no ordering. Workgroup 2 may finish
          before workgroup 0 starts. If two threads in different groups need to agree on something, that is a second
          dispatch.
    • 
        
  • This is the one exception to the rule from earlier that no element knows what any other element is doing. It
          is what makes a sum, a sort or a prefix scan possible on a GPU at all, since each of those needs threads to
          combine their results with each other.
    • 
      

      
      

      

        See it: the compute page prints which workgroup and which thread
        produced every single result.

Vertex and fragment are locked together

      

        You never get one without the other. They are two halves of the same pipeline and always run
        as a pair. Compute is separate, and the useful trick is chaining them: a compute pass writes
        results into a buffer, then a vertex shader reads that buffer and draws them. That is how
        particle systems work, and how a game decides on the GPU what is worth drawing at all before
        drawing any of it.
      

    


    

      
Where TypeScript comes in

      
TypeScript is the manager. It can do the maths, it just should not do the heavy maths.

      
    
        
  • Allocate and upload. Pack numbers into a Float32Array, create a GPUBuffer,
          write the bytes across.
    • 
        
  • Describe. A pipeline object says which shader, which entry points, what the vertex layout is, what
          format the output is.
    • 
        
  • Bind. A bind group connects your buffers to the @group and @binding slots
          the shader declares.
    • 
        
  • Record and submit. An encoder collects a pass worth of commands, queue.submit hands them
          over.
    • 
        
  • Types are real. @webgpu/types means a wrong usage flag or a missing field is a compile
          error, not a black screen.
    • 
        
  • Some maths stays here. The cube demo builds its view projection matrix and every instance matrix in
          TypeScript each frame. That is a few hundred numbers, which is nothing. The split is not maths against no
          maths, it is a bounded amount of setup against millions of identical operations.
    • 
      

      

      

    


    

      
The awkward bits at the boundary

      
Two languages, two memory spaces, and nothing checks that they agree.

      
    
        
  • Layout is manual. A WGSL struct has alignment rules. The Globals block in the cube demo
          is a
          mat4x4f and two vec3f, and it takes 96 bytes because each vec3f pads
          out to 16. Get it wrong and you read garbage, silently.
        
    • 
        
  • Matrices split. A mat4x4f vertex attribute is four slots, one per column, which is why
          the instance layout runs from @location(2) to @location(5).
    • 
        
  • Reading back is a ritual. Storage buffers are not CPU readable. Copy into a buffer created with
          MAP_READ, await mapAsync, take the bytes, unmap.
        
    • 
        
  • Same bytes, two views. The square demo reads one buffer as both Float32Array and
          Uint32Array, because the value is a float and the thread ids are integers.
        
    • 
      

      

      

        See it: the compute page's GPU timings are split into maths only and
        maths plus readback, because the gap between them is the point.
      

    


    

      
Why this is worth caring about

      
Every machine already has this hardware. Until now the web could only use it for pictures.

      

        

          
Data visualisation

          

            Canvas and SVG fall over somewhere around tens of thousands of marks. The GPU draws
            millions of points, edges or map features at 60 frames per second, and can do the layout,
            binning and filtering in a compute pass first. This is why deck.gl and the big charting
            libraries went this way.
          

        

        

          
Heavy data processing

          

            Filtering, aggregating, sorting, image and signal processing, physics. Anything you would
            write as a loop over a big flat array is a candidate. The compute demo runs the same
            Mandelbrot maths on both sides so you can watch the gap.
          

        

        

          
AI

          

            Inference is matrix multiplication, which is the most GPU shaped workload there is.
            WebGPU is the backend that lets ONNX Runtime Web, transformers.js and WebLLM run models
            locally, with no server, no upload, and data that never leaves the machine.
          

        

        

          
Games and 3D

          

            Real engine features rather than a toy: instancing, compute driven particles and culling,
            modern shading. Unity, Unreal and Godot all target WebGPU for web builds.
          

        

        

          
Simulation and digital twins

          

            Fluids, cloth, crowds, N body, cellular automata. Thousands of independent elements
            stepped in parallel, kept in GPU memory between frames and drawn without ever coming back
            to the CPU.
          

        

        

          
Media

          

            Video effects, colour grading, upscaling, computer vision on a webcam feed. Per pixel work
            at frame rate that a CPU cannot keep up with.
          

        

      

    


    

      
Bevy and WebGPU

      
Same standard, different language, one shared implementation underneath.

      
    
        
  • Bevy is a framework, not an engine in the Unity or Unreal sense. There is no editor, no scene tree to
          click around, no asset browser. You write a Rust program, pull in the plugins you want, and it is your
          main that runs. Structurally it is closer to raylib: a set of building blocks handed to you, not
          an application you author content inside.
        
    • 
        
  • It is built on an entity component system. Entities are bundles of plain data and systems are
          functions that run over them, which is the same data oriented shape the GPU wants.
    • 
        
  • Its renderer is wgpu. wgpu is the Rust implementation of the WebGPU standard. Natively it targets
          Vulkan, Metal and D3D12. In a browser it hands straight through to the browser's WebGPU. Firefox's own WebGPU
          implementation is wgpu.
    • 
        
  • Bevy shaders are WGSL. The exact language on the previous slides. A vertex, fragment or compute
          shader written for this demo is the same language you write in Bevy, and since WGSL took its syntax from Rust,
          the shaders and the code around them stop looking like two different worlds.
    • 
        
  • It compiles to WebAssembly. One codebase runs natively and in a tab, with a WebGL2 backend as the
          fallback where WebGPU is missing.
    • 
      

      
Where the link actually comes from

      

        Bevy and WebGPU are not two projects that happen to get on. They meet at wgpu, and wgpu
        exists because Mozilla needed a WebGPU implementation for Firefox and wrote one in Rust.
        That implementation is a normal Rust crate, so Rust code can use it directly rather than
        going through a browser. Bevy's renderer is built on it. So the standard on these slides is
        the thing shipping inside Firefox, and it is also the thing running a native Bevy game with
        no browser anywhere near it.
      

      

        Which means the model carries over one for one. Devices, buffers, bind groups, pipelines,
        encoders and passes are the same objects with the same names. The last slide is a Bevy
        project pushing that model about as far as it goes.
      

    


    

      
The same thing on a server

      
No browser, no window, no screen. wgpu on a rack machine with a GPU in it.

      
      
    
        
  • It is the same crate. wgpu from the previous slide, targeting Vulkan directly with no
          browser anywhere near it. The objects keep their names.
    • 
        
  • Headless is not a mode, it is just leaving something out. You ask for an adapter with no
          surface attached. Nothing opens a window because nothing was ever going to draw.
    • 
        
  • The device is built once and shared. Creating it costs hundreds of milliseconds, so it
          happens at startup and every request borrows it. Buffers get pooled the same way. Per request
          you only record an encoder and submit it.
    • 
        
  • Reading back is the same ritual. Copy into a mappable buffer, await the map, take the
          bytes, unmap. The same four steps as the compute page, and still the expensive part.
    • 
        
  • The awkward bit is the container, not the code. NVIDIA's container runtime mounts CUDA by
          default and not the Vulkan driver, so a machine with a perfectly good card reports no adapter at
          all. NVIDIA_DRIVER_CAPABILITIES has to include graphics.
    • 
        
  • Where it stops. No cuBLAS, no tensor cores, no f64. For kernels you wrote yourself it is
          fine. For training or serving a model, CUDA still wins and it is not close.
    • 
      

      
Which is the Bevy point, one step further out

      

        Devices, buffers, bind groups, pipelines and passes are the same objects with the same names
        whether they are in a tab, in a game, or behind an HTTP handler on a machine with no screen
        plugged into it. The vocabulary from the last sixteen slides is the whole of it.
      

    


    

      
Recap

      
    
        
  • WebGPU is the browser's direct line to the graphics card, and a standard rather than a library.
    • 
        
  • GPUs win on identical work spread over huge amounts of independent data, and lose on everything else.
    • 
        
  • Vertex shaders place points, fragment shaders colour pixels, compute shaders do
          whatever you want with no canvas involved.
    • 
        
  • TypeScript allocates, describes, binds and submits, and does whatever small maths it wants. The bulk work
          goes to WGSL.
    • 
        
  • The hard parts are at the boundary: byte layout, alignment, and the cost of reading anything back.
    • 
        
  • The same model turns up again in wgpu, in Bevy and on a headless server, so none of it is
          wasted.
